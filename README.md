# maintain-readme-arch-md

コードの構造を説明する `readme.arch.md` を点検・新設・更新するスキルです。

対象の技術には慣れていても、初めて読むコードでは、ファイル名だけでは役割やつながりを追いきれないことがあります。このスキルは実コードを読み、「どこから読むか」「どこが何を担当するか」「変更がどこへ影響するか」を短い構造メモにまとめます。

## 使い方

スキルを導入した環境で、対象範囲と作業内容を指定して呼び出します。明示的な依頼があるときに使うスキルで、通常のコーディングに伴う既存readmeの保守では使用しません。

プロジェクト全体を更新する依頼例：

```text
maintain-readme-arch-mdを使って、プロジェクト全体のreadme.arch.mdを更新して。
```

変更せずに点検する依頼例：

```text
maintain-readme-arch-mdのcheckで、src配下のreadme.arch.mdを点検して。
```

| 指定 | 動作 |
| --- | --- |
| `update`（省略時） | 既存の記述を点検・修正し、必要な場所にファイルがなければ新規作成する |
| `check` | 記述の不備、コード変更への追従漏れ、設置不足と修正案を報告する。ファイルは変更しない |

更新時の変更対象は、`readme.arch.md` と、それに直接付随する管理情報です。

## 作成する文書

依頼された範囲のルートと、原則としてソースファイルを含む各ディレクトリに `readme.arch.md` を置きます。自動生成物や外部コピーなど、編集対象ではないファイルだけのディレクトリは除外します。

記載する内容に対応する見出しを、次の順序で使います。短い文書でも情報の種類ごとに見出しで分け、不要な項目や説明を削ることで分量を抑えます。

```markdown
## このディレクトリの目的
## ディレクトリ内分割の意図
## 依存と呼び出しの境界
## 変更時の危険箇所
## 拡張ルール
```

担当する処理、ファイル間の分担、依存の向き、変更時に守る条件などから、読み手の判断に必要な内容だけを記します。

上位の文書にはディレクトリ間の分担と接続を、下位の文書には内部の構造や制約を記載します。文書が全くない場合は、末端から親へ順に作成し、ルートを最後にまとめます。

## 記述の方針

ファイル名や既存の説明だけで判断せず、実コードと必要な呼出元・呼出先・設定・試験を確認します。設計理由の裏付けが見つからない場合は、動機を推測せず、確認できた事実から記載する内容を選びます。

対象の用途や複雑さに応じて記述量を決めます。試作では目的、実装済みの範囲、見落としやすい関係を優先し、数行で足りればそれ以上増やしません。

名前や配置から分かる役割は書かず、すべてのファイル名を列挙する必要もありません。個別の項目はファイル名から書き始め、共通の役割を持つファイルは役割を先頭にして1項目にまとめます。依存関係や変更時の注意は該当する節へ分けます。他の節で言及するファイルは「ディレクトリ内分割の意図」にも必ず載せます。

```markdown
- `file name`：役割・他との分担。
- 役割：`file name`, `file name`, ...
```

関数名を書く場合は、`model.mjs` の `initialState()` のように定義元ファイルを併記します。

調べたことをすべて載せるのではなく、コードを読むために必要な情報に絞ります。関数や設定値の一覧、一般的な技術の解説、階層間で重複する説明は避け、詳しい手順や経緯には既存文書への参照を使います。
